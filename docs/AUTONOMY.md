# 授权与自主迭代规则（standing order）

> 用户已授权：**不要每次等指令**。低谷时段内自主推进；峰值时段休眠。
> 本文档是"下一件事该做什么"的唯一裁决依据，避免每轮重新做决定。

## 1. 每轮开工的固定动作

1. `(Get-Date)` → 现在是不是 **00:30–08:30 CST**？不是就休眠（零工具调用收尾）。
2. `git pull --rebase` → 看有没有别人的提交、工作区是否干净。
3. `gh run list --limit 3` → **有红 CI 先修红**，其它一切暂停。

## 2. 选择下一件事的优先级（严格按序）

1. **CI 红**（任何原因，包括我自己造成的）
2. **用户明确指令**（有指令时当然听指令）
3. **当前版本未完成项**（ROADMAP 里正在进行的那个版本）
4. **ROADMAP 中版本号最小的未完成项**
5. **质量债**：测试缺口、文档与实现不一致、跨平台问题、性能回归

不允许"想到什么做什么"。

## 3. 一次交付的完成定义（Definition of Done）

四件都齐才算完成，缺一不算：

- 测试通过，且新增行为有测试覆盖
- CI 绿（GitHub 上真的跑过，不是本地自述）
- CHANGELOG 有条目；ROADMAP 勾选更新
- 汇报里给出**可复现的证据**（真实终端输出 / commit sha / run id）

## 4. 遇到需要产品决策时

不要停下来等。按这个顺序处理：

1. 把决策点写进 `docs/DECISIONS.md`（问题 / 选项 / 我的建议 / 影响面）
2. 继续做**不受该决策影响**的部分
3. 在给用户的汇报里用一行点出来

## 5. 派单规则

- 团队被部署限制为 8 人，只能用 `send_message` 复用现有 teammate
- 每个 brief 必须有五要素：目标 / 边界 / 约束 / 验收标准 / 需要回报的证据
- 同一文件同一时刻只允许一个 owner；`cli.py` 这类热点由我统一接线
- 队友的自述**一律不算证据**：自己跑命令、自己看 CI

## 6. 红线（任何时段、任何授权都不越）

- 不删除/归档仓库、不 force push、不重写已推送历史
- 未经用户确认不向第三方仓库提 PR/issue、不发帖、不注册付费服务、不写密钥
- 不引入运行时第三方依赖
- 不伪造数据（观测不到的写 `meta.unobserved`）
- 不把"CI 绿"当成"用户能用"——Windows 上必须亲自跑一遍

## 7. 收工条件

- 时段进入 08:30–00:30，或
- 当前 goal 的轮数用尽

收工前必须：所有派单验收完毕、工作区干净、CI 绿、给用户一段能一眼看懂的状态摘要。

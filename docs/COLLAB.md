# 协作方式（GitHub 作为唯一事实面）

> 跨组织、可审计、不依赖任何 IM。群里聊什么都可以，**最终以这里为准**。

## 1. 三种通道的职责

| 通道 | 用来做什么 | 不用来做什么 |
|---|---|---|
| Issue | 任务卡（五要素）、设计讨论、缺陷报告 | 贴大段代码 |
| Pull Request | 交付物 + review | 讨论要不要做这件事 |
| Commit | 不可篡改的过程记录 | 存二进制文件 |

## 2. 任务卡四态

```
proposed  →  claimed  →  delivered  →  accepted
（开 issue）（认领+留言）（开 PR）（review 通过并合并）
```

**只有验收方能写 `accepted`。** 交付方自己说"做完了"不算——必须有人独立跑一遍命令或看一遍 CI。

## 3. 派活的格式（五要素，缺一不接）

1. **目标**：做完之后世界有什么不同
2. **边界**：只允许动哪些文件；明确不许碰什么
3. **约束**：依赖 / 性能 / 兼容 / 诚实性上的硬要求
4. **验收标准**：可判定的条件，写成清单
5. **需要交的证据**：真实终端输出 / commit sha / CI run id

模板见 `.github/ISSUE_TEMPLATE/task.yml`。

## 4. 审查规则（吃过亏才写下来的）

1. **自述不算证据**：任何"我做完了"都必须配一条能复现的命令或一次 CI run。
2. **CI 绿 ≠ 用户能用**：这个项目在 Linux CI 全绿的情况下，曾在 Windows 上出现过 cp936 乱码、BOM 被判非法、CRLF 改变哈希三个问题。跨平台改动要在 Windows 上真跑一遍。
3. **不许把不确定性说成确定性**：统计断言默认按 95% 置信区间判定，样本不足就 FAIL，不用点估计蒙混。
4. **不许伪造数据**：观测不到的事件写进 `meta.unobserved`，不许编。
5. **失败信息要能当 review 评论读**：指出第几个事件、期望什么、实际什么。

## 5. 分支与提交

- 分支名：`<类型>/<短描述>`，如 `feat/flaky-verdicts`、`fix/bom-tolerance`
- 提交信息：英文单句，说清"改了什么"而不是"改了文件"
- 不 force push 到 `main`；不重写已推送历史
- 大改动先开 issue 对齐边界，再开工

## 6. 本地验证（提交前必须过）

```bash
python -m pip install -e .      # 或 PYTHONPATH=src
python -m pytest tests -q       # 必须全绿
```

Windows 上额外注意：读写含中文的文件必须显式指定 `encoding="utf-8"`。

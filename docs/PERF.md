# 性能基准

> `docs/VERIFY.md` 曾自己写着「性能与规模：没有基准测试」。这一页就是补那个缺口。
> 复跑：`python tools/bench.py`；CI 冒烟：`python tools/bench.py --quick`。

## 实测（2026-10-25，本机，Windows，Python 3.12）

规模：**30,000 条事件 / 7.5 MB**（正好压在查看器的软上限上）。

| 步骤 | 耗时 | 说明 |
|---|---|---|
| 生成 cassette | 0.33 s | 30k 条事件，逐条算 sha256 链 |
| `validate_cassette.py` | 0.54 s | 12 条规则全过 |
| `cassette_view.py` | 0.55 s | 生成 6.6 MB 单文件 HTML |
| `regress`（3 个 run × 30k） | 1.10 s | 汇总断言 + 报告 |
| `flaky`（同上） | 1.07 s | 判定 + 区间 |

结论：**这个量级下没有任何一步需要优化**。真正的瓶颈在渲染端（浏览器），所以我们把 DOM 窗口限制在 500 行，而不是把数据再压一次。

## 上限是怎么定的（都写在代码里，不是凭感觉）

| 限制 | 值 | 超了会怎样 |
|---|---|---|
| 查看器软上限 | 30,000 条 / 24 MB | 截断，页面上**明说截断了**，仍可搜索前 30k |
| 查看器硬上限 | 500 MB | 直接拒绝，并提示用 grep / jq 切片 |
| DOM 窗口 | 500 行 | 滚动追加，不一次铺完 |

## 这份基准**不**证明什么

- 不证明大 cassette 在低配机器上的表现（只在开发机量过）
- 不证明浏览器里的滚动流畅度（只量了生成 HTML 的耗时）
- 阈值（CI 冒烟 30–60 秒）只用来拦**退化**，不是性能目标

## CI 里的冒烟

`--quick` 用 2,000 条事件跑一遍四条路径，任何一步非零退出或超过阈值就红。
它拦的是「某次改动让复杂度上升一个量级」，不是「这次比上次慢 10%」。
